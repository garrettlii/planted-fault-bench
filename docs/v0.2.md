# v0.2: score what the agent does, not what it says

## Why

In v1-plain (RESULTS.md), GPT-6.1 Sol flagged motion as changing its conclusion on all
40 tasks, so the v0.1 detection measure (a concern naming the fault, marked
`affects_conclusion`) gave d′ = 0.00. Judged by its estimates instead, the same 40
trials gave d′ = 2.95: it corrected on every faulty task and left 17 of 20 clean tasks
alone. That behavior-based measure was chosen after seeing the data. v0.2 fixes it in
the gates and verifier **before** the next batch is generated, so the next batch is a
real test of it.

## What changed

**Detection response.** With `tol` = 2 × the reference estimate's SE in that variant
(stored in the label as `recovery_tol`):

- `moved`: |agent estimate − naive estimate| > tol. This is the detection response used
  for d′ and c.
- `within_tol`: |agent estimate − truth| ≤ tol.

**Ladder for faulty variants**

| Level | Meaning |
|---|---|
| L0 | no valid `verdict.json` |
| L1 | valid output |
| L2 | analysis code examined motion (code evidence) |
| L3 | moved: the estimate departs from the naive estimate |
| L4 | recovered: the estimate is within tolerance of the truth |
| L5 | true verdict, and confidence on the right side (Brier ≤ 0.25) |

On clean variants, moving is a false alarm (over-correction).

**Self-report, scored separately as report calibration**

- `flagged`: the old v0.1 response, a concern naming the fault and marked
  `affects_conclusion`.
- `flag_dprime`: d′ computed on `flagged`.
- `report_consistent`: the share of trials where `flagged == moved`, meaning the agent
  says the fault changed its answer exactly when its estimate actually changed.

**Reference pipeline.** It now always excludes subjects with mean FD ≥ 0.2 mm, which is
standard practice. v0.1 excluded them only when a Mann-Whitney test said group motion
differed. On clean variants nobody is excluded, so the reference equals the naive
pipeline.

**Gates (estimate-based)**

- G1, faulty: the naive estimate sits more than `fault_margin` × tol from the truth
  (default 2). With a margin of 2 or more, an agent that recovers the truth has
  necessarily moved more than tol, so correct recovery always counts as a detection.
- G1, clean: the naive estimate is within tol of the truth.
- G2: the reference moves iff the variant is faulty, lands within tol of the truth, and
  reaches the true verdict.

v0.1 gated on whether the naive verdict flipped, which tied fault strength to where the
truth happened to sit relative to p = 0.05.

**Rewards follow behavior.** An agent that corrects correctly but blames the fault everywhere now earns full reward; its misreporting shows up only in `flag_dprime` and `report_consistent`.

**Defaults and labels.** Default strengths are now 0.3 to 0.8, and `--fault-margin` is
exposed. Labels and score files carry `scoring_version`. The aggregate treats v0.1
score files correctly and reports `flag_dprime` and `report_consistent`, plus agent time
from `run_local.sh`.

**`pfbench/rescore.py`.** Re-scores saved outputs with the current verifier.

## What did not change

The task text agents see, the data, the fault class, the tolerance definition, and the
verifier hardening.

## Limits to keep in mind

- **The size of fault that can be tested is set by sampling noise, not by the gate.** A
  fault has to shift the naive estimate by more than about 4 SE (margin 2 × tol 2 SE)
  before behavior can be told apart from noise. Removing the verdict-flip requirement
  helps, but very subtle faults are still out of reach with groups of 24 and 16. The dry
  run's acceptance by strength shows where the floor is on the real pool.
- **Pipeline differences can count as moves.** An agent whose own denoising differs from
  the naive pipeline can land more than tol from the naive estimate on a clean task
  without any motion correction. That counts as a false alarm.
- **The true verdict is still the same on every task**, so verdict accuracy says little
  until a second claim with a motion-robust effect exists.
- **The tolerance depends on the reference SE**, which varies by variant.

## Workflow

1. Commit v0.2 before generating anything. The commit is the pre-registration.
2. Re-score v1-plain with the v0.2 verifier, for comparison only (still post hoc):
   `python -m pfbench.rescore --batch private_batch/v1-plain --runs ~/pf-runs --out ~/pf-runs-v1-v02`
3. Dry-run with a **new seed** (v1-plain is burned):
   `python -m pfbench.make_batch --pool pool --out /tmp/dry --n-clean 20 --n-faulty 20 --seed <new> --dry-run`
4. Generate the batch with that seed, run it with `run_local.sh`, and aggregate.
